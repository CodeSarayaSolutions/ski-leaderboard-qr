# Server-only Supabase HTTP setup

This is a local, unapplied change. No live configuration, database, deployment or publication was changed. The previous sanitized source is preserved at `<local-backup-directory>`. Unity/B18 are untouched.

## Configuration contract

Privately set these existing names in the ignored app `.env.local` or your server's secret environment. Never paste secret values into chat, source, command arguments or browser configuration.

| Variable | Meaning |
| --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | HTTPS origin of your Supabase gateway, e.g. `https://supabase.example.org`; no path, user info, query or fragment. Requests use `/rest/v1/rpc/...`. This is the Supabase origin, not the public leaderboard origin. |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Accepted as an existing environment name but **unused**. Leave blank for this app. It is never a fallback. |
| `SUPABASE_SERVICE_ROLE_KEY` | Server-only legacy Supabase JWT whose role is `service_role`. The gateway verifies its signature. Missing, expired, anonymous or malformed values fail closed before HTTP. Opaque `sb_secret_...` keys are not supported by this legacy self-hosted JWT contract. |
| `NEXT_PUBLIC_SUPABASE_DB_SCHEMA` | Must equal `velo-leaderboard`. This denotes the private **data** schema, not the HTTP API profile. Any other value fails closed. |

No direct PostgreSQL runtime connection or `DATABASE_URL_*` is used. Existing private environment files were not edited or printed. Keep `EVENT_ID`, `APP_ORIGIN`, session and admin settings as documented in README. Public admin still requires its separate strong credential; the database service key is never an admin sign-in credential. The production repository entry imports `server-only`; client components do not reference these variables or import the repository. The browser only calls the Next app's same-origin API.

The API profile is deliberately fixed to **`alpine_qr_api`**; it is not user-selectable. The Node server sends both `Content-Profile` and `Accept-Profile` with that value, plus server-only apikey/Authorization headers. It cannot select an arbitrary RPC/table from a user request. Exactly seven RPCs exist: lookup_key, receipt_status, submit, list_scores, list_keys, register_key, revoke_key. All transport calls are POST, bounded by a five-second timeout and 1 MiB response limit, no-store, with redirects refused. There are no automatic write retries. A later deliberate resubmission is idempotent even if an earlier response was lost after commit. Upstream errors, bodies and headers are never returned or logged.

## Operator migration and gateway order

1. Back up the database. Review the existing additive `migrations/001_official_qr.sql`, then the new `migrations/002_server_rpc.sql`. Apply **001 then 002** personally as an authorized migration owner on your chosen environment. 002 creates no rows, resets nothing and changes no legacy table privileges/defaults/policies. The optional manual reset is unrelated and must not be run as part of this setup.
2. 002 expects the existing Supabase `service_role`. It creates an isolated NOLOGIN/NOINHERIT `qr_api_owner`, with no role memberships, superuser, RLS bypass, database/role creation or replication rights. That owner receives only private schema USAGE and exact existing internal function EXECUTE capabilities. Its wrappers use a fixed `pg_catalog` search_path and fully qualified calls. The internal 001 functions retain the atomic insert, locks, uniqueness, revocation checks and private contacts. No underlying table grants are added for this transport.
3. The dedicated API schema contains no tables or views. Function grants inherited from the migration owner's defaults are revoked before the transaction commits; only service_role receives wrapper EXECUTE and schema USAGE. PUBLIC, anon and authenticated receive neither. Future functions created as the new wrapper-owner role default to no PUBLIC EXECUTE. Existing owners' global default privileges are untouched. Namespace collisions or unsafe inherited access fail the migration. Do not grant anonymous/authenticated membership in service_role or qr_api_owner. Do not add unrelated objects to this API schema.
4. On your self-hosted PostgREST configuration, add **`alpine_qr_api`** to the existing exposed schemas (`PGRST_DB_SCHEMAS`, or the deployment's equivalent `db-schemas` setting), retaining unrelated existing API schemas. Do **not** add `velo-leaderboard` to exposed schemas or extra search paths for this app. No legacy namespace exposure or new legacy read permission is needed. If a legacy application already exposes it, assess that separately; this change does not alter its live config or claim to hide an existing exposure.
5. Reload/restart the intended PostgREST configuration and schema cache using your deployment's documented mechanism. This SQL intentionally does not perform reload notifications or edit a gateway. Keep the existing authenticator/service-role JWT integration; do not add anon/authenticated wrapper grants to fix a gateway error.
6. Privately set the four names above and restart the Next server only after approval. If you rerun 001 later, rerun 002 afterward because 001 intentionally removes nonstandard grants on its private functions. Each migration is rerunnable in that order and preserves rows. No application startup automatically applies SQL.

## Service-role trust boundary

A service_role credential has an intrinsically broad blast radius and bypasses RLS where its database grants permit access. These wrappers restrict **this application's chosen HTTP surface**, not the key itself. The same stolen key can exercise other service-role capabilities already enabled in the Supabase project. Both claim and admin database calls now use that single powerful server credential; the former separate direct-DB login separation is no longer present. Keep it on the server, rotate it if exposed, suppress request-body/header logging in proxies/APM, restrict server access and avoid other public service-role endpoints. Do not put it in `NEXT_PUBLIC_*`, client code, generated public assets or a browser Supabase client. The app's signature verification and authenticated admin routes are the authorization boundary; someone holding the service key is already trusted and can bypass the application verifier.

Signature verification requires a **read-only** key lookup first. No claim write occurs until the Node verifier checks the signed payload, scope, device/event, activation/revocation and age, and validates form contacts. Preview/status remain read-only. The existing SQL submit function rechecks revocation and serializes first-write-wins. Duplicate responses contain no contact details. Admin contact responses remain authenticated, private/no-store and same-origin protected.
